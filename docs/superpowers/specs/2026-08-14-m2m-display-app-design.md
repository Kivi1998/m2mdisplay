# M2M Display App 设计文档

日期：2026-08-14
状态：已确认，待写实现计划

## 背景

现有 M2M Display 是两个命令行程序（`M2MSender` / `M2MReceiver`），只能通过 SSH/终端手动编译、拷贝、启动、杀进程。核心的低延迟架构（虚拟显示器 + ScreenCaptureKit + VideoToolbox + 独立光标通道）已经验证有效，延迟远优于 AirPlay。但作为长期日用工具，命令行操作方式不符合非开发者的使用习惯，也没有可见的运行状态、没有出错提示、没有失败自动恢复。本设计把它封装成一个带图形界面的 App。

## 目标

- 两台机器（MacBook Pro、iMac）装同一个 App，启动时选角色。
- 提供菜单栏界面完成角色、连接方式、分辨率的选择，以及开始/停止投屏。
- 投屏可以随时打开、随时关闭，关闭后 iMac 恢复成完全正常可用的桌面。
- MacBook 和 iMac 都能各自触发开始/停止，两边状态保持同步。
- 出错要有清晰的状态提示和日志，常见的意外中断能自动恢复。

## 非目标（本次不做）

- 自动发现对端设备（Bonjour/mDNS）——固定两台机器，手动填一次 IP 成本很低，不值得引入额外复杂度和故障点。
- 支持两台以上机器，或者动态更换搭档设备。
- 面向他人分发所需要的代码签名、公证、独立安装包——目前只供自己长期使用。
- iMac 本地键盘鼠标反向控制 MacBook（不是本项目范围，输入源仍然是 MacBook 单向）。

## 产品形态

**一个统一 App，角色在启动时选择**（而非拆成 SenderApp / ReceiverApp 两个独立 App）。两台机器装同一份安装包，首次启动选"发送端"或"接收端"，选择会记录在本机（`UserDefaults`），下次自动带出。理由：只服务这两台固定机器，拆成两个 App 除了让职责更"纯粹"之外没有实际收益，反而多一份要同步维护的发布物。

App 以**菜单栏图标（menu bar extra）**形式常驻，不占 Dock、不开主窗口。点击图标弹出状态面板。

## 菜单栏面板内容

- 角色选择：发送端 / 接收端
- 连接方式：雷雳（固定 IP）/ 手动填 IP
- 分辨率：预设下拉（1920×1080 / 3840×2160 / 自定义）
- 开始 / 停止投屏（主按钮）
- 实时状态：当前状态（未启动/权限检查中/启动中/运行中/重连中/出错/已停止）、延迟、帧率
- 最近事件列表：最新几条日志事件的简要展示
- 打开日志文件（跳转到日志所在目录）
- 权限状态：逐项列出当前角色需要的权限，缺失的标红并提供跳转系统设置的入口

## 状态机

```
未启动 (Idle)
  用户点"开始投屏"
    ↓
检查权限 (CheckingPermissions)
    缺权限 → 权限引导（提示具体缺哪个 + 跳转系统设置按钮 + "重新检查"按钮）
    权限齐全 → 启动中
    ↓
启动中 (Starting)
    发送端：确保虚拟显示器存在（见下方"虚拟显示器生命周期"）→ 开始抓屏编码 → 连接 iMac 视频端口 → 启动鼠标监听
    接收端：确保正在监听端口 → 等待发送端连接
    失败（虚拟显示器创建失败、端口占用等）→ 出错，提供"重试 / 停止"
    成功 → 运行中，并通知对端"我已开始"
    ↓
运行中 (Connected)
    视频流意外中断（SCStream 停止 / TCP 断开）→ 自动进入重连中，只重启断掉的那一环，不需要整个 App 重启
        重连成功 → 回到运行中
        连续重试 N 次仍失败 → 出错，人工点"重试"或"停止"
    用户或对端触发"停止投屏" → 停止中 → 回到未启动，并通知对端"我已停止"
```

发送端和接收端各自维护自己的状态机实例；"运行中"要求双方都处于运行中，任一方停止都会通知另一方跟着回到未启动。

## 虚拟显示器生命周期（发送端）

早期方案让虚拟显示器在发送端 App 启动时创建、退出时才销毁，以减少重复创建时的模式注册竞态。实际日用验证发现，这会在“停止投屏”后继续保留第二块 macOS 显示器：放在该屏幕上的 App 窗口仍留在不可见桌面，用户看不到也点不到。

当前方案改为：**点击“开始投屏”时异步创建并严格校验虚拟显示器，点击“停止投屏”时销毁虚拟显示器并等待 WindowServer 确认其离线**。显示器离线后，macOS 会把其上的窗口迁回仍在线的 MacBook Pro 内置屏幕。下次开始投屏时重新创建干净的虚拟显示器；已有的后台创建、重试、HiDPI 模式校验和关闭镜像逻辑继续负责规避系统竞态。

## 投屏开关与 iMac 画面切换

iMac 只有一块物理屏幕，没有硬件级别的"信号源切换"能力。软件层面的等价实现是：接收端始终有一个可以随时显示/隐藏的全屏覆盖窗口。

- **投屏关闭**：覆盖窗口隐藏（`orderOut`），恢复 Dock、菜单栏、iMac 自己的系统光标——iMac 处于完全正常、可以自己使用的状态，接收端 App 只在后台监听，不影响任何东西。
- **投屏打开**：覆盖窗口显示，隐藏 Dock/菜单栏，隐藏 iMac 原生光标，进入沉浸展示模式，行为与现在的实现一致。

## 双向控制

MacBook 和 iMac 都能各自触发开始/停止：

- **MacBook**：菜单栏面板的按钮，另外可选配一个全局快捷键（这台机器本来就要处理抓屏/输入监控权限，加一个全局热键不算新增权限负担）。
- **iMac**：
  - **全局热键**（默认建议 `⌃⌥⌘S`，可在设置里改）：不论当前投屏开着还是关着，按一下即可切换状态。因为要在"投屏关闭、其他 App 在前台"时也生效，这**必须是全局热键**，需要给接收端 App 授予"输入监控"或"辅助功能"权限——这是本次新增需求带来的必然依赖，会体现在权限引导流程里。
  - **紧急强制关闭**（沿用现有三击 Esc 机制）：仅在投屏开着、覆盖窗口是前台时生效，使用应用内本地事件监听，不需要额外权限，作为热键失灵时的最后手段。

**状态同步**：协议里新增一条轻量的"状态变更通知"消息（开始/停止/心跳），任一端触发状态变化都要广播给对端，确保双方菜单栏面板显示的状态一致，不会出现一边显示"运行中"、另一边显示"已停止"的不一致情况。

## 权限引导

按角色列出所需权限，用不弹系统对话框的方式静默检测（`CGPreflightScreenCaptureAccess()`、`IOHIDCheckAccess` 等），缺失项在面板里标红，提供"打开系统设置"按钮直接跳转到对应权限页面，以及"重新检查"按钮（系统不会在授权后主动通知 App，需要手动刷新）。

| 角色 | 所需权限 | 用途 |
|---|---|---|
| 发送端 | 屏幕录制 | ScreenCaptureKit 抓屏 |
| 发送端 | 输入监控 | 全局鼠标监听 |
| 接收端 | 输入监控 | 新增的全局热键开关 |

接收端的"三击 Esc 紧急关闭"不需要权限（应用内本地监听）。

## 日志

两端各自把关键事件写入持久化日志文件（`~/Library/Logs/M2MDisplay/`），区分两类事件：

- **用户主动操作**：启动、停止、切换角色/配置——正常事件，不触发自动重连。
- **意外中断**：连接断开、抓屏流终止、编解码失败等——触发状态机的自动重连逻辑，同时记录具体原因（错误码/错误信息）。

菜单栏面板的"最近事件"列表实时展示最新几条，"打开日志文件"按钮跳转到日志目录，供需要时查看完整历史。

## 代码结构调整

现有 `Sources/M2MSender/main.swift`、`Sources/M2MReceiver/AppDelegate.swift` 里的核心逻辑（虚拟显示器管理、抓屏编码、网络收发、鼠标监听、光标渲染）基本保留，改造成可以被 UI 驱动的引擎类（例如 `SenderEngine` / `ReceiverEngine`），暴露启动/停止方法和状态回调，替代现在"进程启动就自动跑、写死配置常量"的写法。`M2MShared` 里的协议定义扩展，新增状态变更通知消息类型。现有的命令行入口（`M2MSender`/`M2MReceiver` 可执行文件）可以保留作为开发调试用途，或者后续被 App 完全取代。

## 测试方式

沿用项目已有的"只在 iMac 上验证接收端效果，绝不在 MacBook 上本地运行接收端"的规则；新增的双向控制、状态同步、自动重连逻辑需要额外验证：
- 分别从 MacBook 和 iMac 两侧触发开始/停止，确认另一端状态正确同步。
- 人为制造一次抓屏流中断（现有已知问题），确认自动重连逻辑生效、日志记录正确。
- 验证投屏关闭后 iMac 本身操作不受任何影响（Dock、菜单栏、光标均恢复正常）。
